# Internationalisation (i18n)

## Rule

No user-facing string is ever written as a Python literal. Every message a
user can see (report text, CLI output, validation issue text) comes from
the message catalog via the language manager
(`context.lm.text("<key>", **params)`), never an f-string or hardcoded
sentence.

## Message keys

Actual format, superseding this section's earlier `<area>.<RULE-ID>.<kind>` draft (the
convention that shipped, per the "Implemented" note below): `rule.<RULE-ID>.<kind-or-slug>`,
e.g. `rule.DESC-003.error`, `rule.COMP-011.warning`, `rule.DESC-002.must_start_at_one` (a rule
with several distinct message templates gets one slug per template, not one generic `.error`
for all of them). A rule's shared "required column is missing" abort case reuses one key per
sheet domain, `rule.<sheet_domain>.missing_required_column` (e.g.
`rule.description.missing_required_column`), across every rule on that sheet rather than
duplicating the same sentence under every rule ID.

Cross-cutting checks that are not tied to one specific sheet-and-rule pair (the model-level
structural/data-cleaning checks under the `STRUCT-`/`CLEAN-` prefixes, `.specs/business-rules/
README.md`) follow the same `rule.<RULE-ID>.<kind>` shape for the rule-identified message (e.g.
`rule.STRUCT-009.cell`, `rule.CLEAN-001.error`), plus a shared `rule.file_cleaning.<slug>`
namespace for the handful of generic, reused-by-every-`CLEAN-0XX`-id sub-messages (e.g.
`rule.file_cleaning.value_not_integer`) that would otherwise duplicate word-for-word under six
different rule IDs.

Legacy keys still use the old `verification_name_*` /
`validator_*_error_*` snake_case convention — do not invent new legacy-style
keys; new rules use the `rule.*` format even before their sheet is fully
migrated, and the mapping lives in `.specs/business-rules/README.md`.

Implemented (DOC-003, 2026-09-13): every rule the migration has ported —
all nine `rules/*.py` registries (structure, description, composition,
temporal reference, value, scenario, legend, proportionality, spell) —
renders exclusively through `rule.*` keys (77 keys per locale; see
`.specs/i18n/catalog.md`'s key-inventory table). The surviving legacy
prefixes (`verification_name_*`, `fs_utils_*`, `validator_structure_*`,
`model_report_*`, `loader_error_*`) are titles and utility/loader-layer
strings, not business rules, and stay as-is by design — they are not a
migration backlog, just a naming convention this rule does not require
retrofitting onto non-rule strings.

Extended (ARC-005, Phase 5, 2026-09-13): the same `rule.*` convention now also covers the
model-level structural/data-cleaning checks (`STRUCT-008…012`, `CLEAN-001…006`, plus `DESC-011…
012`/`SCEN-001…002`/`VAL-001`/`PROP-001…002`'s in-model messages) that had not been ported to a
`rules/*.py` registry yet — 31 more keys per locale (108 total), rendered via `self.context.
language_manager.text(...)` from inside `models/sp_*.py` and its message-building helpers
(`helpers/common/{formatting,processing,validation}/*.py`), not from a rule module. `legend_
processing.py`'s `LEG-001…011` (~25 messages) are the largest still-open piece of this gap — see
`.specs/quality/backlog/03-architecture.md#ARC-005`.

## Catalogs

- Catalogs live at `static/locales/{pt_BR,en_US}/messages.json`.
- Every key added to `pt_BR` gets its `en_US` counterpart in the same
  commit — no key exists in one locale only. `tools/i18n_check.py`
  (`/i18n-check`) verifies parity and flags unused/orphan keys.
- Placeholders are named (`{sheet_name}`, `{row}`, `{code}`), never
  positional (`{}`, `{0}`) — a translator must be able to reorder them.
- Portuguese text belongs only inside the message catalogs and inside the
  generated report/CLI output the end user reads. Everywhere else — code,
  identifiers, comments, docs, commit messages — is English.

## Never do

- Never hardcode a Portuguese or English sentence in a validator, model, or
  report module.
- Never add a key to only one locale file.
- Never use positional/unnamed placeholders in a message template.
