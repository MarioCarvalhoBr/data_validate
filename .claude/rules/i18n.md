# Internationalisation (i18n)

## Rule

No user-facing string is ever written as a Python literal. Every message a
user can see (report text, CLI output, validation issue text) comes from
the message catalog via the language manager
(`context.lm.text("<key>", **params)`), never an f-string or hardcoded
sentence.

## Message keys

Target format for new/migrated rules: `<area>.<RULE-ID>.<kind>`, e.g.
`description.DESC-003.error`, `composition.COMP-011.warning`. `<area>`
matches the sheet/domain (`description`, `composition`, `values`,
`temporal_reference`, `scenarios`, `legend`, `proportionality`,
`file_structure`, `spelling`); `<kind>` is `error` or `warning`.

Legacy keys still use the old `verification_name_*` /
`validator_*_error_*` snake_case convention — do not invent new legacy-style
keys; new rules use the target format even before their sheet is fully
migrated, and the mapping lives in `.specs/business-rules/README.md`.

## Catalogs

- Catalogs live at `static/locales/{pt_BR,en_US}/messages.json`.
- Every key added to `pt_BR` gets its `en_US` counterpart in the same
  commit — no key exists in one locale only. `tools/i18n_check.py`
  (`/i18n-check`) verifies parity and flags unused/orphan keys.
- Placeholders are named (`{sheet_name}`, `{row}`, `{code}`), never
  positional (`{}`, `{0}`) — a translator must be able to reorder them.
- Portuguese text belongs only inside the message catalogs and inside the
  generated report/CLI output the end user reads. Everywhere else — code,
  identifiers, comments, docs, commit messages — is English.

## Never do

- Never hardcode a Portuguese or English sentence in a validator, model, or
  report module.
- Never add a key to only one locale file.
- Never use positional/unnamed placeholders in a message template.
